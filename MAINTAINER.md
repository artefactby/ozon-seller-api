# MAINTAINER.md

Справочник для разработчика и паблишера этого репозитория. Это не инструкция для
ИИ-агентов: их правила находятся в `AGENTS.md`.

## Назначение репозитория

Репозиторий публикует пакет `artefactby-ozon-seller-api` — transport-only
типизированный клиент Ozon Seller API без runtime-зависимостей. Исходный OpenAPI
снимок не хранится в git: в репозитории коммитятся только сгенерированные артефакты
из `src/generated/`.

## Предварительная настройка

### Инструменты

- Node.js `>= 20.19` для локальной разработки и dev toolchain.
- npm и доступ на публикацию в пакет на npmjs.com.
- Права на push в GitHub-репозиторий и создание/merge pull request.

### Пути инструментов

Скрипты синхронизации работают с фиксированными путями (см. `scripts/lib/paths.mjs`):

- `temp/swagger.json` — локальный снимок спецификации;
- `temp/api-sync-report.md` — отчёт синхронизации.

Пути захардкожены сознательно: двух значений недостаточно, чтобы оправдать
слой конфигурации.

### Разовая настройка GitHub и npm

Автопубликация опирается на GitHub Actions и trusted publishing в npm:

1. npmjs.com → пакет → Settings → Trusted Publisher:
   `artefactby` / `ozon-seller-api` / `release.yml`.
2. GitHub → Settings → Actions → General → включить
   `Allow GitHub Actions to create and approve pull requests`.
3. Включить branch protection на `main`: обязательный pull request и
   обязательные проверки. Matrix-джоба CI регистрирует проверки под именами
   с версией Node, поэтому в списке required checks выбираются фактические
   имена: `test (20)`, `test (22)`, `test (24)` и `runtime-node18`.

Без этих настроек ветки и PR будут работать, но автооткрытие PR и автопубликация
могут не сработать.

## Ежедневная разработка

### Установка зависимостей

```bash
npm ci
```

### Основные команды

- `npm run typecheck`
- `npm test`
- `npm run build`
- `npm run codegen`

### Обычный кодовый change set

Если меняется рантайм, типовые хелперы, README, тесты или лимитер:

1. Создайте рабочую ветку от актуального `main`.
2. Внесите изменения.
3. Прогоните как минимум `npm run typecheck`, `npm test`, `npm run build`.
4. Если правите пользовательскую документацию, обновляйте `README.md` и
   `README.en.md` вместе.
5. Если change set должен попасть в релиз, обновите `CHANGELOG.md` и `version`
   в `package.json` до merge в `main`.
6. Откройте pull request в `main`.

Публикацию, тег и GitHub Release запускает только merge в `main`, если версия в
`package.json` ещё не имеет тега `v<version>`.

## Синхронизация со спецификацией Ozon

Это основной релизный сценарий.

### 1. Снимок спецификации

Скачайте свежий `swagger.json` вручную из `https://docs.ozon.ru/api/seller/swagger.json`
и положите его в `temp/swagger.json`.

Автоматически тянуть файл не надо: docs.ozon.ru защищён антиботом.

### 2. Автоподготовка ветки

```bash
npm run api-sync
```

Что делает скрипт:

- требует чистое рабочее дерево и запуск из `main`;
- делает `git pull --ff-only origin main`;
- читает манифест поверхности API из `HEAD` (без него завершается с подсказкой
  о бутстрапе — см. раздел «Манифест поверхности API»);
- создаёт ветку `api-sync/YYYY-MM-DD` (или `-2`, `-3`, если дата уже занята);
- запускает `npm run codegen`, затем `typecheck`, `test`, `build`;
- сравнивает манифесты старого и нового снимков и пишет отчёт в
  `temp/api-sync-report.md`;
- коммитит изменения в `src/generated/`, помещая текст отчёта в тело коммита;
- пушит ветку в `origin`.

Если кодогенерация не меняет `src/generated/`, ветка удаляется, и скрипт
завершается без релиза. Если падает любой шаг после создания ветки, ветка и
изменённые файлы остаются на месте для диагностики, а скрипт печатает точные
команды отката.

### 3. Pull request

Push в ветку `api-sync/**` автоматически запускает:

- `.github/workflows/ci.yml` — проверки;
- `.github/workflows/create-pr.yml` — открытие pull request в `main`;
  описание pull request включает отчёт синхронизации из тела коммита.

### 4. Мини-ревью релиза

Выполняется на ветке `api-sync/*` после `npm run api-sync`; в Cursor —
командой `/api-sync-release`. Задача: сверить обновление, описать его в
`CHANGELOG.md`, поднять версию, закоммитить и запушить. Публикацию, тег и
GitHub Release после merge делает CI — их не трогать.

#### Входные данные

1. `temp/api-sync-report.md` — отчёт скрипта синхронизации (счётчики,
   добавленные и удалённые пути, breaking changes). Тот же текст доступен
   в теле коммита синхронизации и в описании pull request.
2. Дифф сгенерированных артефактов: `git diff main...HEAD -- src/generated`.
3. Данные об обновлении Ozon — при наличии. Формат значения не имеет:
   текстовые release notes, уведомление из Telegram, скриншот из личного
   кабинета. Это дополнительный слой сверки, подтверждающий, что снимок
   спецификации свежий и целый; технически типы генерируются и без него.
   Если данных нет, сверка пропускается, а в записи CHANGELOG фиксируется,
   что сверка с анонсом Ozon не проводилась.
4. При необходимости — свежий снимок спецификации `temp/swagger.json`.

#### Порядок работы

1. Прочитать отчёт. Если в нём «Breaking changes: обнаружены» — см. раздел
   «Breaking changes» ниже.
2. При наличии данных об обновлении сверить каждый их пункт с диффом типов:
   изменение либо отражено в диффе, либо явно фиксируется как не попавшее в
   снимок (для таких пунктов в CHANGELOG есть раздел `### Notes` — см. запись
   0.2.0). Изменения в диффе, которых нет в анонсе, тоже описываются.
3. Выбрать версию (пакет в 0.x):
   - только описания и документация → patch;
   - добавления (новые пути, поля, значения enum) → minor;
   - breaking changes → версию не выбирать, остановиться (см. ниже).
4. Дописать раздел в `CHANGELOG.md` в существующем стиле: заголовок
   `## [X.Y.Z] - YYYY-MM-DD`, вводная строка «Синхронизация снимка OpenAPI
   Seller API с обновлениями Ozon от …», счётчики путей и схем из отчёта,
   фраза про рантайм («Рантайм клиента не менялся (`http-methods` без
   изменений)», если это так), затем `### Added` / `### Changed` / `### Notes`.
   Язык — русский, стиль — как в предыдущих записях.
5. Поднять `version` в `package.json` (только правка поля, без `npm version` —
   тег ставит CI).
6. Закоммитить оба файла в стиле истории
   (`Document the OpenAPI sync in CHANGELOG; version X.Y.Z.`) и запушить ветку.
7. PR готов к merge; после merge релиз произойдёт автоматически.

#### Breaking changes

Сигналы: удалённые пути или схемы, смена HTTP-метода, удалённые или
переименованные поля, изменение подписи типа или флага required. При любом
таком сигнале:

- готовится черновик раздела CHANGELOG с блоком `### Removed` / `### Breaking`
  и миграционными заметками (что удалено, чем заменяется по анонсу Ozon);
- версия НЕ выбирается и НЕ коммитится: черновик показывается человеку, и
  решение о выпуске с breaking changes принимает он (пока пакет в 0.x, это
  обычно `0.(y+1).0`).

#### Ограничения мини-ревью

- `src/generated/**` руками не редактировать — только через `npm run codegen`.
- Никаких `npm publish`, `git tag`, `gh` — релиз делает CI после merge.
- Никаких реальных Client ID, API-ключей и производственных данных в примерах
  и тексте.

### 5. Merge и публикация

После merge pull request в `main` workflow `.github/workflows/release.yml`:

1. проверяет, что тега `v<version>` ещё нет;
2. выполняет `npm ci`;
3. публикует пакет в npm через trusted publishing (OIDC, без токенов);
4. ставит тег `v<version>`;
5. создаёт GitHub Release с текстом из текущего раздела `CHANGELOG.md`.

Локально выполнять `git tag`, `gh release create` и `npm publish` в штатном потоке
не нужно.

### Манифест поверхности API

`src/generated/manifest.json` — компактная проекция снимка спецификации: пути с
HTTP-методами и схемы с подписями полей (типы, `required`, значения enum).
Генерируется `npm run codegen` вместе с остальными артефактами и коммитится.

Назначение: снимок спецификации в git не хранится, поэтому `api-sync`
восстанавливает предыдущее состояние API из манифеста в `HEAD` и
детерминированно сравнивает его с поверхностью свежего снимка. Это даёт
детекцию breaking changes до уровня полей: удаление путей, схем и полей, смена
HTTP-метода, изменение подписи типа и флага required. Семантику изменившейся
подписи (сужение или расширение) оценивает ревьюер.

Манифест — входные данные для сравнения, а не часть пакета: `files` в
`package.json` публикует только `dist/` и `README.en.md`, рантайм манифест не
импортирует, поэтому на размер устанавливаемого пакета он не влияет вовсе.
Решение принято осознанно: цена — примерно мегабайт в git-репозитории
(между синхронизациями меняется малая часть строк, история растёт медленно),
польза — строке «Breaking changes: не обнаружены» в отчёте можно доверять без
вычитки всего диффа `types.ts`.

Руками файл не редактируется — только через `npm run codegen`. Если `api-sync`
сообщает, что в `HEAD` манифеста нет (бутстрап на новой машине или после
переписывания истории), выполните `npm run codegen` на снимке, соответствующем
`HEAD`, и закоммитьте манифест в `main`.

## Правила версионирования

Пакет пока находится в `0.x`, поэтому решения такие:

- только правки описаний, комментариев и документации → `patch`;
- добавления путей, полей, схем, значений enum → `minor`;
- удаление путей или полей, переименование, сужение типов, смена HTTP-метода →
  breaking change; релиз обычно `0.(y+1).0`.

При breaking changes решение всегда принимает человек. Автоматика и ИИ могут
подсветить сигнал, но не должны самостоятельно выбирать версию такого релиза.

## Что считается доказательством готовности

Перед merge change set считается готовым только если:

- `npm run typecheck` зелёный;
- `npm test` зелёный;
- `npm run build` зелёный;
- CI на ветке зелёный;
- `CHANGELOG.md` и `package.json` согласованы с ожидаемым релизом.

## Ручной fallback

Если trusted publishing временно недоступен, можно публиковать вручную, но это
аварийный путь, а не норма:

```bash
npm publish --provenance=false
```

После ручной публикации тег и GitHub Release всё равно нужно синхронизировать
осознанно, чтобы состояние репозитория и npm не расходилось.
